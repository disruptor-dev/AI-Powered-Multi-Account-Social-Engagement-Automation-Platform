# Social Engagement Platform — Phases 1–6

A deliberately small, runnable foundation for a multi-account YouTube + Instagram comment-management SaaS.

## What Phase 1 includes

- Next.js App Router + TypeScript frontend with an initial status dashboard.
- FastAPI backend with liveness (`/health`) and readiness (`/ready`) endpoints.
- PostgreSQL connection using SQLAlchemy 2.x and psycopg 3.
- Alembic migration setup, including a minimal `workspaces` table.
- Redis connection plus a lightweight worker process skeleton for future background jobs.
- Docker Compose for local development.
- Environment-variable based configuration, CORS setup, tests, and API docs.

## Current phase coverage

Phase 1 provides the app/database/Redis foundation. Phase 2 adds secure owner authentication, OAuth connections, and encrypted credential storage. Phase 3 adds the durable YouTube + Instagram comments inbox, comment/media deduplication, synchronization, external YouTube video imports, YouTube replies, and reviewed multi-channel top-level comment publishing. Phase 4 adds AI-assisted reply drafts and configurable comment rules that queue drafts for human review; **automation never publishes a public reply automatically**. Phase 5 adds workspace team membership, role-based access control, invitations, and audit history. Phase 6 adds independently selectable workspaces, a signed active-workspace session claim, and tenant-scoped APIs so each client/brand can keep accounts, comments, drafts, automation rules, invitations, and audit history separate. Phase 7 adds encrypted transactional-email delivery, member password recovery with session revocation, Redis-backed operation-specific rate limits, and request/security response headers. SSO/MFA, billing, and workspace archive/delete lifecycle remain future work.

## Requirements

Recommended easiest setup:

- Docker Desktop with Docker Compose v2
- Git
- A browser

For running services without Docker, install Python 3.12+, Node.js 22+, PostgreSQL 16/17, and Redis 7. The current Next.js documentation requires Node.js 20.9 or newer; Node.js 22 is the recommended baseline for this scaffold.

## Quick start (Docker Desktop)

Run these commands from the project root.

### Windows PowerShell

```powershell
Copy-Item .env.example .env
docker compose up --build
```

### macOS / Linux

```bash
cp .env.example .env
docker compose up --build
```

The first startup downloads images and installs dependencies. When all containers are healthy, open:

- Frontend: http://localhost:3000
- API root: http://localhost:8000/
- API liveness: http://localhost:8000/health
- API readiness (checks PostgreSQL and Redis): http://localhost:8000/ready
- Interactive API docs: http://localhost:8000/docs
- OpenAPI JSON: http://localhost:8000/openapi.json

The API container runs `alembic upgrade head` before starting Uvicorn in this **local development Compose setup**. For production, run migrations as a controlled one-off deployment step before routing traffic; do not make multiple API replicas race to run migrations at startup.

Stop containers with `Ctrl+C`, then:

```bash
docker compose down
```

This preserves your local database and Redis volumes. To permanently delete local development data as well, use `docker compose down -v` — this is destructive and removes the named volumes.

## Architecture choices (kept intentionally simple)

- **Modular monolith:** one API service with separate modules, not microservices.
- **Synchronous SQLAlchemy:** easier to reason about for this initial foundation; async DB access can be introduced only if measured needs justify it.
- **PostgreSQL:** durable system of record.
- **Redis:** future job queue/cache foundation. The current worker is a scaffold and intentionally has no social-platform jobs yet.
- **No secrets or social API keys:** OAuth is not part of Phase 1.
- **Health vs readiness:** `/health` reports that the API process responds; `/ready` checks PostgreSQL and Redis availability.

## Troubleshooting

### Port already in use

Change `API_PORT`, `FRONTEND_PORT`, `POSTGRES_PORT`, or `REDIS_PORT` in `.env`. If changing the host API port, update `NEXT_PUBLIC_API_URL` to match, e.g. `http://localhost:8010`.

### API reports database not ready

```bash
docker compose logs postgres api
docker compose ps
```

Confirm `DATABASE_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` match. If the database volume was created using different credentials, changing `.env` alone will not rewrite that volume's user/password. For disposable local data only, `docker compose down -v` removes it so the DB initializes again.

### Frontend cannot reach API

Open `http://localhost:8000/health` directly first. Check `NEXT_PUBLIC_API_URL` and `CORS_ORIGINS`. The browser connects to the host-mapped API port, not the Compose-only hostname `api`.

### Compose says `.env` is missing

Copy `.env.example` to `.env` at the repository root before starting Compose.

# Phase 2 — Secure account connections

Phase 2 adds a single configured owner login, signed HTTP-only session cookies, CSRF protection, the account-connection API, Google/YouTube OAuth, Instagram Login OAuth for Business/Creator accounts, encrypted token storage, a one-time OAuth state table, account listing/disconnect, and explicit token refresh.

## Important scope boundary

At the end of Phase 2 this was a single-owner starting point. Phase 5 adds invited members and server-enforced workspace roles for the existing default workspace. It does not add independently creatable/switchable client workspaces or replace the environment-configured owner login. Account endpoints are restricted to owner/admin roles, and the UI never receives access/refresh tokens.

## 1. Add the Phase 2 environment variables

Keep your existing `.env` (do not overwrite it). Copy the Phase 2 variables from `.env.example` into `.env`, then replace placeholders and save the file. For local Docker Compose, the backend reads these environment variables from `.env` automatically.

Generate three secrets/hashes inside the backend image after a build:

```powershell
# Generate a password hash (replace the sample with a strong password of 12+ characters).
docker compose run --rm api python -c "from argon2 import PasswordHasher; print(PasswordHasher().hash('ReplaceWithYourStrongPassword'))"

# Generate a random session signing key.
docker compose run --rm api python -c "import secrets; print(secrets.token_urlsafe(48))"

# Generate the Fernet key used to encrypt stored social OAuth tokens.
docker compose run --rm api python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Place the outputs in `APP_ADMIN_PASSWORD_HASH`, `SESSION_SECRET_KEY`, and `TOKEN_ENCRYPTION_KEY` respectively. Set `APP_ADMIN_EMAIL` to your login email. Since Argon2 hashes contain `$`, wrap the hash value in single quotes in `.env`, e.g. `APP_ADMIN_PASSWORD_HASH='$argon2id$v=19$...'`, so Compose does not interpolate `$` segments. Never commit `.env` or share these values. **Back up `TOKEN_ENCRYPTION_KEY` securely**: if it is lost or changed, existing encrypted tokens can no longer be decrypted and the accounts must be reconnected.

## 2. Configure Google / YouTube OAuth

1. Open [Google Cloud Console](https://console.cloud.google.com/), choose/create a project, enable **YouTube Data API v3**, and configure the OAuth consent screen.
2. Create an OAuth Client ID of type **Web application**.
3. Add this exact Authorized redirect URI for local development: `http://localhost:8000/api/v1/accounts/youtube/callback`.
4. Copy the client ID and client secret into `YOUTUBE_CLIENT_ID` and `YOUTUBE_CLIENT_SECRET`.
5. During OAuth consent screen testing, add each Google account you want to connect as a test user. Public apps requesting YouTube scopes may need Google verification and/or an API compliance/quota audit before production use.

Requested scope: `https://www.googleapis.com/auth/youtube.force-ssl`. This allows the later comment workflows planned for this product; ask only for permissions the product actually needs and explain them to account owners.

## 3. Configure Instagram Login

1. Create/select a Meta app at [Meta for Developers](https://developers.facebook.com/apps/).
2. Add the Instagram product / **Instagram API with Instagram Login** setup.
3. Register this exact redirect URI in the Instagram login settings: `http://localhost:8000/api/v1/accounts/instagram/callback`.
4. Copy the Instagram App ID and App Secret into `INSTAGRAM_APP_ID` and `INSTAGRAM_APP_SECRET`.
5. Test with Instagram **Business or Creator** accounts and grant `instagram_business_basic` plus `instagram_business_manage_comments`. App Review / advanced access may be needed for accounts outside app roles/testers.

The implementation pins the Meta Graph API version via `META_GRAPH_API_VERSION` (currently `v26.0`). Check Meta's version changelog and your app dashboard before upgrades. Redirect URIs must exactly match the provider configuration. For any non-local deployment, use HTTPS and update both backend callback URIs and the corresponding provider settings. Set `APP_ENV=production`, `CORS_ORIGINS` to the exact frontend origin, `FRONTEND_APP_URL` to that origin, and `SESSION_COOKIE_SAMESITE=none` only if the frontend/API are truly cross-site (secure cookies are then forced). Prefer a custom domain with frontend and API on the same site; browsers may block third-party cookies across unrelated hosted domains even with `SameSite=None`.

## 4. Run migrations and start

```powershell
docker compose up --build
```

The API container runs `alembic upgrade head` before starting FastAPI. If you already had Phase 1 running, the migration adds `social_accounts` and `oauth_states`; it does not recreate or delete `workspaces`.

Open:

- Frontend: <http://localhost:3000>
- API docs: <http://localhost:8000/docs>
- Readiness: <http://localhost:8000/ready>

Log in with `APP_ADMIN_EMAIL` and the password that matches your Argon2 hash. In **Accounts**, choose Connect YouTube or Connect Instagram and finish the official provider consent flow. No real account will be created in the dashboard until the provider callback succeeds.

## Phase 2 API routes

- `GET /api/v1/auth/csrf` — issue/return a CSRF cookie and token for the browser.
- `POST /api/v1/auth/login` — owner login; sets an HTTP-only session cookie.
- `GET /api/v1/auth/me` — current owner/workspace information.
- `POST /api/v1/auth/logout` — end session.
- `POST /api/v1/accounts/youtube/connect` — create one-time state and return Google authorization URL.
- `GET /api/v1/accounts/youtube/callback` — exchange code, discover owned channels and store encrypted credentials.
- `POST /api/v1/accounts/instagram/connect` — return Instagram authorization URL.
- `GET /api/v1/accounts/instagram/callback` — exchange code, upgrade to a long-lived token, fetch profile and store encrypted credentials.
- `GET /api/v1/accounts` — list account metadata; never returns token values.
- `POST /api/v1/accounts/{account_id}/refresh` — explicitly refresh the connected account's token.
- `DELETE /api/v1/accounts/{account_id}` — locally disconnect and erase stored token values.

Every browser POST/DELETE must send `X-CSRF-Token` matching the `socialdesk_csrf` cookie and include credentials. OAuth `state` values are random, stored hashed, expire after 10 minutes, are provider/owner-bound, and can be consumed only once.

## Token and disconnection behaviour

Tokens are encrypted at rest with Fernet and are never serialized into API responses or browser storage. The Google refresh token is retained for backend refresh. Phase 3 refreshes expired or near-expiry credentials as part of scheduled/manual comment sync when provider refresh credentials remain valid; invalid or revoked credentials move the account to `reauthorization_required`. Local disconnect clears this app's stored credentials; it does not guarantee revocation at Google/Instagram, so also remove the app in the relevant provider's security/connected-app settings when you need full revocation.

# Phase 3 — Unified comments inbox and synchronization

Phase 3 is additive. It keeps the Phase 1/2 tables and OAuth flows and applies two additive Alembic migrations (`20261026_0003` and `20261026_0004`) to add sync state, create `media_items`, `social_comments`, and `comment_sync_runs`, and store targeted video-import metadata. Existing connected accounts and their stored encrypted credentials are preserved.

## What is implemented

- **One inbox:** comments across connected YouTube channels and Instagram professional accounts are shown in the same view, with account/platform filters, text/author/post search, open/resolved state, unanswered/answered filtering, optional reply rows, newest/oldest sorting, and server-side pagination.
- **YouTube sync:** reads the authorized channel's uploads playlist and discovers videos, including Shorts (Shorts use the same official `commentThreads` comment API). Retrieves root comment threads and expands available replies within configured limits. Videos that disable comments are treated as partial-sync warnings rather than failing the whole account.
- **External video import:** paste a public `youtube.com/watch`, `youtu.be`, Shorts, embed, or live-video URL and explicitly select a connected YouTube channel. Import runs through the background worker; status can be polled and comments are stored under the chosen channel for later filtering and reply context. Videos/comments that are private, deleted, restricted, missing, or not API-accessible are reported as unavailable rather than bypassing YouTube permissions.
- **Reply publishing:** publish a reply to a top-level YouTube comment using the selected connected YouTube channel. The server refreshes near-expiry tokens, rechecks platform and OAuth scopes, sends the reply via `comments.insert`, mirrors the successful reply into local inbox storage, and updates the root comment’s reply state. The API can still reject replies when the selected channel is not eligible for that thread.
- **Instagram sync:** reads media and supported comments/replies from the connected professional account using the existing Instagram Login token and granted permissions. Account type, app review, permission approval, and Meta API availability still govern what data the provider returns.
- **Idempotent storage:** `(social_account_id, platform_media_id)` and `(social_account_id, platform_comment_id)` are unique. Repeated syncs update provider-owned fields while preserving local `open`/`resolved` workflow state.
- **Background jobs:** a Redis queue carries sync jobs; the worker records queue/run status in PostgreSQL, schedules connected accounts at the configured interval, prevents duplicate active runs per account, marks stale runs after worker crashes, and sends malformed/unsupported messages to a dead-letter list.
- **Webhook acceleration:** valid signed Instagram `comments` notifications queue a sync for the matching connected account. The webhook is a signal to read current provider state, not a trusted content source.
- **Security:** all inbox and sync APIs require the Phase 2 owner session. Mutating routes also require the existing double-submit CSRF token. OAuth credentials are decrypted only server-side in the API/worker paths that need them; tokens are not included in inbox responses, job payloads, or sync error messages.
- **Dashboard:** the unified inbox provides account-level sync health, queued/running/partial/error states, recent metrics, manual sync, status polling, local resolve/reopen controls, empty/loading/error states, and responsive layout.

## Inbox/API contract

All endpoints below are under `/api/v1` and require the logged-in owner session except the existing public signed webhook endpoint.

- `GET /comments` — query parameters: `platform=youtube|instagram`, `account_id`, `query`, `workflow_status=open|resolved|all`, `response_status=unanswered|replied|all`, `include_replies`, `since`, `until`, `sort=newest|oldest`, `page`, and `page_size` (maximum 100). Returns `items`, pagination metadata, and applied filters.
- `GET /comments/summary` — open, unanswered, resolved, and total comment counts, accounts requiring attention, and most recent account sync time.
- `GET /comments/sync-status` — account-level sync state and recent run records; never returns provider tokens.
- `POST /comments/sync` — queues one account when sent `{ "account_id": "..." }`, or all connected accounts when sent `{}`. Requires `X-CSRF-Token` matching the CSRF cookie. A sync already queued/running is reused rather than duplicated.
- `POST /comments/external-video` — body `{ "account_id": "...", "video_url": "https://www.youtube.com/watch?v=..." }`, with CSRF protection. Queues a targeted import for a public video under the selected connected YouTube channel. A different active sync for that channel must finish first.
- `GET /comments/runs/{run_id}` — owner-authenticated status for a background sync/import job; includes only sanitized status, counts, and target video ID.
- `POST /comments/{comment_id}/reply` — body `{ "account_id": "...", "text": "..." }`, with CSRF protection. Publishes the reply on YouTube from the explicitly selected connected channel and stores the resulting reply in the inbox. Only YouTube replies are currently supported by this mutation endpoint.
- `PATCH /comments/{comment_id}/status` — body `{ "workflow_status": "open" | "resolved" }`, with CSRF protection. This changes only this app's local inbox status; it does not mutate the provider comment.
- `GET /api/v1/webhooks/instagram` and `POST /api/v1/webhooks/instagram` — Meta verification and signature-validated notifications. Configure the callback URL and subscribe the Meta app to the `comments` webhook field if that feature is approved for the app.

## Multi-channel top-level YouTube comment publisher (incremental feature)

The inbox also includes a **manual-review-first** publisher for a one-off batch of distinct top-level comments on a target YouTube video. This is separate from replying to an existing thread.

- Select 1–10 connected YouTube channels with the `youtube.force-ssl` OAuth scope.
- Paste a public video, Shorts, or supported YouTube URL.
- Enter one comment per selected channel in selection order. Commas and newlines delimit comments; wrap a comment containing a comma or a line break in double quotes. A literal double quote inside a quoted value is escaped as `""`. The UI displays the channel-by-channel preview before enabling submission.
- Confirm both that the drafts have been reviewed and that they are genuine, relevant, distinct, and not intended to manipulate engagement. Identical normalized text is rejected within a batch.
- Publishing runs sequentially in the Redis worker. Each channel gets its own durable status (`queued`, `publishing`, `published`, `failed`, or `unknown`), and the dashboard polls the batch result. A mixed result is kept as `partial`; failed channels do not hide successful channels.
- The worker does not blindly retry a `publishing` item whose outcome may be unknown after a crash or lost connection. Check YouTube before trying uncertain items again. It also prevents re-publishing the same normalized text for the same channel/video when an earlier item is published, in-flight, or uncertain.
- The request estimates quota as one video metadata lookup plus 50 units per comment insert. YouTube still enforces daily quota, channel authorization, video state, comment settings, policy rules, and API-side restrictions.

### Multi-channel publish API

All routes require the existing authenticated owner session. `POST` additionally requires the existing CSRF token.

- `POST /api/v1/comments/publish-batches` — accepts `{ "video_url": "...", "comments": [{"account_id": "...", "text": "..."}], "idempotency_key": "...", "confirm_publish": true, "confirm_nonspam": true }`. The API validates workspace ownership, connected YouTube status, OAuth scope, channel count, unique account IDs, distinct normalized text, and idempotency. Returns a durable batch ID and per-channel initial states.
- `GET /api/v1/comments/publish-batches/{batch_id}` — returns workspace-scoped batch counts and per-channel results. It never returns OAuth tokens.

### Migration and verification

The incremental migration is `20261026_0005_multi_channel_comment_publishing` and follows `20261026_0004`. Docker Compose should apply it via the project's existing Alembic upgrade step. Verify with `docker compose exec api alembic current` and then run `docker compose exec api pytest -q`. Before live use, test a short, relevant comment on a video where YouTube permits comments and confirm the posted comment appears from the intended channel.


## Phase 4 — AI reply copilot and review-first automation

Phase 4 adds contextual AI suggestions and comment-matching rules without changing the provider account model or enabling automatic public publishing.

### AI draft setup

Set the following variables in the backend environment (never in a `NEXT_PUBLIC_*` frontend variable):

- `AI_REPLY_ENABLED=true` enables draft generation.
- `AI_API_KEY` is the secret for the OpenAI-compatible provider.
- `AI_BASE_URL=https://api.openai.com/v1` is the provider API root.
- `AI_MODEL=gpt-4o-mini` chooses a chat-completions model available to your provider account.
- `AI_REQUEST_TIMEOUT_SECONDS=25` sets the request timeout.
- `AI_MAX_OUTPUT_TOKENS=280` bounds the model response size.
- `AI_DRAFT_MAX_COMMENTS_PER_RULE_RUN=500` caps new draft attempts in one automation run.
- `AUTOMATION_RULE_INTERVAL_SECONDS=300` controls the scheduled rule evaluation interval (bounded to 60–86400 seconds).
- `AUTOMATION_RULE_LOOKBACK_LIMIT=1000` bounds the number of recent comments considered per run (maximum 2000).

Restart/rebuild the backend and worker after changing backend environment variables. The settings endpoint reports only whether AI is configured and the chosen provider/model; it never returns credentials. The AI provider receives the selected public comment text and media title, plus the optional instruction text that you type. Do not place secrets, private customer data, or sensitive personal information in comments or custom instructions. Review every generated draft for accuracy and tone before use.

### AI reply draft workflow

1. Open **Unified inbox** and select a comment that you want to answer.
2. Choose tone, language, and optional short guidance, then click **Generate AI draft**.
3. The background worker requests a suggestion; the saved draft appears with its status and an editable text field.
4. Edit and save as needed, then approve or reject it. For supported top-level YouTube comments, **Approve & use in reply** loads the exact approved text into the existing reply composer. The owner must still explicitly publish it; modifying text afterward requires re-approval.
5. On Instagram, drafts can be copied for manual use. Instagram reply publishing is not included in this phase.

Draft states are persisted (`queued`, `generating`, `draft`, `approved`, `rejected`, `published`, `failed`). Provider credentials remain server-side. Provider failures are stored as stable error codes rather than raw response bodies. A reply whose provider outcome is unknown is not blindly retried.

### Draft-only comment automation rules

Open **Automation** in the left navigation. Create a rule with a unique name, optional connected-account filters, a platform, required/optional/excluded keywords, author substring, minimum likes, reply/open/unanswered filters, tone, language, and custom guidance. Rules can be enabled/disabled, edited, run manually, inspected through run counters and per-comment executions, or deleted.

Scheduled and manual rules only **queue AI drafts for review**. There is intentionally no automation rule action that sends comments or replies to YouTube or Instagram. The rule executor skips comments it has already processed, tracks failures, bounds the lookback/draft count, and recovers old queued jobs after a worker restart. A failed draft execution can be retried by a subsequent rule run; successful/prior executions are not duplicated.

## Phase 5 — Workspace team access, role permissions, and audit log

Phase 5 adds invited team members to the existing default workspace while preserving the configured `APP_ADMIN_EMAIL` / `APP_ADMIN_PASSWORD_HASH` owner login. It is an additive migration (`20261027_0007`) that creates local member identities, workspace memberships, single-use invitations, and append-only audit events. Existing OAuth tokens, connected social accounts, comments, AI drafts, and automation rules are preserved.

### Roles and permissions

- **Owner** — the configured environment owner; full access. The owner cannot be demoted, suspended, or removed through the team API.
- **Admin** — can manage connected accounts, invite members, update/remove non-admin members, and read the audit log. Only the owner can promote another administrator or modify an admin.
- **Editor** — can synchronize and manage comments, generate/review AI drafts, manage draft-only rules, and explicitly publish authorized comments/replies. Editors cannot manage connected accounts or workspace membership.
- **Viewer** — read-only access to workspace accounts, inbox, summaries, drafts, rules, and member directory. Mutating routes enforce the role on the backend even if a client attempts to call them directly.

Suspended or removed members are rechecked against the database on every authenticated API request; a still-valid signed cookie does not preserve access. Team member passwords are hashed with Argon2 and are never returned by the API. The session cookie remains HTTP-only and state-changing endpoints continue to require the existing double-submit CSRF check.

### Invitations and join flow

1. The owner or an admin opens **Team & access** and creates an invitation with an email and role.
2. The API stores only a SHA-256 digest of a cryptographically random token and returns the acceptance URL once. The link is single-use and expires after seven days.
3. There is no email-delivery provider configured in this phase; copy the returned link and send it to the intended recipient through an approved channel. Do not post it publicly.
4. The invitee opens the link, sets a name and a password of at least 12 characters, and accepts the invitation. The API creates the member identity/membership and signs the invitee in.
5. Admins can revoke pending invitations, change eligible member roles/status, remove members, and inspect the audit log. Removed accounts are disabled; a fresh invitation is required to rejoin.

The initial limit is 25 active members plus pending invitations within the capacity guard. Invitations to the configured owner email are rejected. Raw invitation tokens, passwords, OAuth credentials, access tokens, and refresh tokens are not recorded in audit events.

### Phase 5 API routes

All authenticated routes use the existing owner/member session cookie. Unsafe methods require CSRF:

- `GET /api/v1/team/capabilities` — current role and safe permission flags.
- `GET /api/v1/team/members` — workspace member directory.
- `GET /api/v1/team/invitations` — invitation history without token values; admin/owner only.
- `POST /api/v1/team/invitations` — create an invitation and return its one-time acceptance URL; admin/owner only.
- `DELETE /api/v1/team/invitations/{invitation_id}` — revoke a pending invitation; admin/owner only.
- `POST /api/v1/team/invitations/accept` — accept a single-use token, create/activate the account, and establish a member session.
- `PATCH /api/v1/team/members/{user_id}` — update an eligible member's role or active/suspended state.
- `DELETE /api/v1/team/members/{user_id}` — remove a member and disable their local identity.
- `GET /api/v1/team/audit-log?limit=50&offset=0` — paginated team/invitation audit events; admin/owner only.
- `POST /api/v1/auth/login` accepts either configured-owner credentials or an invited member's credentials; `GET /api/v1/auth/me` includes role and member ID.

## Phase 6 — Multiple independent workspaces

Phase 6 extends the Phase 5 membership model so one user can belong to multiple workspaces with a different role in each. Each workspace has a stable unique slug, name, memberships, connected social accounts, comment/media records, reply drafts, automation rules, publishing batches, sync history, invitations, and audit events scoped by `workspace_id`.

### Workspace workflow

1. Owners/admins open the workspace selector in the sidebar and choose **New workspace** to create an isolated client/brand workspace. The creator becomes an owner within that new workspace, and the session switches to it.
2. The selector lists only workspaces where the signed-in identity has an active membership. Choosing another workspace calls the server-side switch endpoint; the API verifies membership and reissues the HTTP-only signed session with the selected workspace ID.
3. Each API request validates the selected workspace against the database membership. The workspace ID in a browser request is never accepted as authorization by itself.
4. Owners/admins can rename a workspace they own/administer. The stable slug does not change after rename. Workspace deletion/archival is intentionally not included because it requires lifecycle handling for queued jobs and retained data.
5. Team members and invitations are scoped to the active workspace. The same email identity may accept separate invitations to different workspaces by entering its existing password; each workspace retains its own role and invitation/audit history.

### Phase 6 API routes

All state-changing routes require the existing CSRF token. Authenticated calls require a session with an active membership:

- `GET /api/v1/workspaces` — list workspaces available to the current user, including per-workspace role and active selection.
- `POST /api/v1/workspaces` — create a workspace; requires owner/admin role in the current workspace and enforces a 25-workspace-per-user limit.
- `POST /api/v1/workspaces/switch` — switch to a workspace ID only when the user has an active membership there; reissues a signed session with the new active workspace claim.
- `PATCH /api/v1/workspaces/{workspace_id}` — rename a workspace only when the user has owner/admin membership in that target workspace.
- `GET /api/v1/auth/me` — returns the selected workspace after the session has been switched.

Creating and switching workspaces writes an audit event. The active workspace context is applied to account listing/connect/disconnect/refresh, comments and external-video imports/replies, multi-channel publish batches, AI drafts, automation rules/runs, team member lists, invitations, and audit events. OAuth callbacks re-check that the actor still has an active admin/owner membership in the workspace where authorization started.

## Phase 7 — Security hardening, transactional email, and account recovery

Phase 7 adds a durable encrypted email outbox, SMTP delivery for workspace invitations and member password-reset links, one-time password-reset tokens, session-version revocation, Redis-backed rate limiting for sensitive endpoints, and request correlation/security response headers. These changes are additive (migration `20261027_0009`) and preserve existing workspaces, social accounts, comments, drafts, and connected OAuth credentials.

### Configure transactional email

Set these **backend-only** environment variables in `.env` / your deployment secret store. Keep `TOKEN_ENCRYPTION_KEY` configured because email messages containing one-time links are encrypted at rest.

| Variable | Purpose |
|---|---|
| `SMTP_HOST`, `SMTP_PORT` | SMTP endpoint (usually port 587 with STARTTLS or 465 with implicit TLS) |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Optional SMTP authentication; keep the password secret |
| `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME` | Sender identity |
| `SMTP_STARTTLS`, `SMTP_USE_SSL` | Transport security; use one appropriate mode for the provider |
| `SMTP_TIMEOUT_SECONDS` | Bounded connect/send timeout |
| `EMAIL_OUTBOX_MAX_ATTEMPTS` | Maximum retries before a message is marked failed |
| `EMAIL_OUTBOX_POLL_SECONDS` | Worker polling interval |
| `PASSWORD_RESET_TTL_MINUTES` | Reset-link lifetime (the service bounds this to 5–120 minutes) |

The outbox encrypts message subjects/bodies with `TOKEN_ENCRYPTION_KEY`; database status records store only the recipient, message kind, lifecycle, attempt count, and stable error code. A worker sends queued messages and retries transient failures with bounded exponential backoff. A worker crash during SMTP delivery can result in a harmless duplicate email because SMTP does not offer exactly-once delivery; invitation and password-reset tokens remain single-use. Do not log or forward reset/invitation URLs.

When SMTP is configured, invitations are queued for delivery and the inviter can still copy the single-use link as a fallback. If SMTP is not configured, invitations retain the existing copy-link flow. An SMTP failure does not silently remove an invitation; the UI reports when email queueing failed so the inviter can use the link. Password-reset requests always return the same public message whether the email exists, is eligible, or delivery is unavailable to reduce account enumeration.

### Password recovery

- `POST /api/v1/auth/password-reset/request` — CSRF-protected, rate limited, enumeration-resistant request; eligible active invited-member identities receive a one-time link by email.
- `POST /api/v1/auth/password-reset/confirm` — CSRF-protected, rate-limited, consumes the token, updates the Argon2 password hash, invalidates outstanding reset tokens, records workspace audit events, and increments the user's session version.
- `GET /api/v1/auth/csrf` — provides the double-submit token required by unsafe requests.

The configured bootstrap owner cannot use this flow because its password hash is managed through `APP_ADMIN_PASSWORD_HASH`; rotate that password through your secret-management procedure. Password reset is for invited workspace-member identities. After a successful reset, all previously issued member sessions are rejected and the user must sign in again. The reset token digest—not the raw token—is stored in the security-token table.

### Rate limiting and proxy deployment

Redis-backed atomic fixed-window limits protect login, password reset, invitation creation/acceptance, OAuth start/refresh/disconnect, comment synchronization, external-video import, AI draft requests, comment replies, and multi-channel publishing. Defaults are deliberately conservative and configurable: login is 10 attempts/minute per client IP, password recovery 5/hour, invitations 10/minute, and sensitive social actions 30/minute. Limits apply to each operation bucket independently. HTTP 429 responses include `Retry-After`.

`RATE_LIMIT_ENABLED=true` enables the limiter. If `RATE_LIMIT_FAIL_CLOSED` is unset, development fails open on Redis unavailability while staging/production fail closed with HTTP 503. Do not disable limits in public deployments. By default the limiter uses the socket peer address and ignores `X-Forwarded-For`. Set `RATE_LIMIT_TRUST_PROXY_HEADERS=true` only if a trusted reverse proxy strips client-supplied forwarding headers and writes its own. A spoofable forwarded header makes IP-based limits ineffective. Redis is shared across API replicas, so limits remain coordinated.

The API also attaches a sanitized `X-Request-ID`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`. In production requests already marked HTTPS by the deployment stack receive HSTS; terminate TLS at a trusted proxy and configure forwarded-scheme handling safely in your deployment.

### What the dashboard reports

- **Operational KPIs:** incoming and root comments, connected-account replies and new top-level comments, resolved/unanswered comments, response rate, average response time, average resolution time, comment likes, publishing success/failure/unknown outcomes, AI draft counts, automation-rule execution counts, and connected-account status.

- **Provider performance:** latest daily channel/account snapshot, insight permission/sync state, recent refresh jobs, and top videos/posts with media-level metrics when the provider returns them.

YouTube Analytics requires the additional read-only OAuth scope `https://www.googleapis.com/auth/yt-analytics.readonly`. Provider metric names and eligibility vary. YouTube channel daily reporting requests views, likes, comments, shares, estimated minutes watched, subscribers gained, and subscribers lost. ### Metric interpretation and history limitations

- Operational data is calculated from records the app has actually stored. The first reporting period does not reconstruct historical activity that was never imported into the app.

- Data from provider snapshots starts only when Phase 8 sync is first run; the product will not backfill older snapshots unless the provider's reporting API supplies dated daily rows.

## Human-only YouTube top-level comment queue

Migration `20261027_0013` changes the Human YouTube Comment Queue to **manual text only**. AI reply drafts and automation remain separate tools, but they do not write text into this public top-level comment queue.

### Manual-only workflow and public-write boundary

1. `POST /api/v1/comments/youtube-queue` accepts the selected YouTube account, one target video URL, one idempotency key, and `comment_text` written or pasted by the user. The API fetches target video metadata for display and account/video validation, then stores the supplied text in `draft_text` with `draft_source='human'` and status `pending_approval`. No AI service, AI queue, prompt, tone selector, or text-generation request is called.
2. The frontend shows the human-written text immediately under **Pending Approval**. The user may edit it, checks the selected channel and video, confirms relevance/non-spam, and chooses a timezone-aware `scheduled_at` value at least one minute in the future and no more than 30 days ahead.
3. The approval API refuses any item whose `draft_source` is not `human`, rechecks account permission and quality warnings, stores the exact final approved text, and transitions it atomically to `scheduled`.
4. At the selected time, the worker atomically claims a due row, rechecks the account and OAuth scope, and calls YouTube `commentThreads.insert` with the exact approved text. It does not call an AI service or alter the text.
5. Confirmed provider outcomes become `posted` or `failed`; quota exhaustion pauses the queue; uncertain writes become `outcome_unknown` and are never retried automatically.

### Legacy queue migration

- The old `POST /api/v1/comments/youtube-queue/generate` endpoint returns HTTP 410 Gone. It cannot trigger AI generation.
- Migration `20261027_0013` adds the `draft_source` column and classifies all existing Phase 9 rows as `legacy_ai`. Existing unapproved AI items (`queued_generation`, `generating`, `pending_approval`, `scheduled`, `blocked_quota`) are cancelled during migration so they cannot be published after deployment. A row already in `publishing` is marked `outcome_unknown`, because a provider write may already have happened and must be manually checked. Posted legacy records remain historical records with `draft_source='legacy_ai'`.
- The worker’s legacy generation handler drains old queued Redis messages by cancelling the corresponding queue item. It never calls the model for this queue.
- The separate AI Reply Copilot and draft-only automation features are unchanged; they are not the Human YouTube Comment Queue. The generic text-quality check is in `app.services.comment_text_quality` and does not generate text.

### Target and repetition safeguards

- A partial unique index prevents more than one active/posted/unknown queue item for the same target video in a workspace, regardless of selected account. A channel may hold only one active queue item at a time.
- A normalized text fingerprint blocks reuse of the same approved text across active/posted items in a workspace. This does not detect all semantic paraphrases; review and meaningful, non-repetitive use are still required.
- The legacy `POST /api/v1/comments/publish-batches` endpoint returns HTTP 410. Do not use this queue for repetitive, misleading, mass, or coordinated engagement. Manual approval and scheduling do not guarantee policy compliance.

### API reference

- `POST /api/v1/comments/youtube-queue` — create a queue item from manually authored `comment_text`; returns `pending_approval` immediately.
- `POST /api/v1/comments/youtube-queue/generate` — retired; returns HTTP 410.
- `GET /api/v1/comments/youtube-queue?limit=50` — read the active workspace queue and queue pause state.
- `POST /api/v1/comments/youtube-queue/{id}/approve` — save exact user-approved text, selected time, and confirmation flags. The API requires `draft_source='human'`.
- `POST /api/v1/comments/youtube-queue/{id}/cancel` — cancel an unpublished item.
- `POST /api/v1/comments/youtube-queue/{id}/resolve-outcome` — Owner/Admin-only manual resolution of an uncertain provider write after checking YouTube directly.
- `POST /api/v1/comments/youtube-queue/quota/resume` — resume after an admin verifies quota availability.

All write routes use existing session, workspace-role, CSRF, and configured rate-limit protections. Queue records include source attribution, final text, approval/schedule/execution timestamps, provider comment ID, attempts, and safe error codes.
